# CaloriVoice — техническое описание (MVP)

Документ фиксирует стек и хранение данных для первой версии: **календарь + дневник еды за день + голосовой ввод**. Иконки блюд и быстрый доступ (Shortcuts, виджеты, Watch) — **вне scope MVP**.

См. продуктовые опоры: [main-ideas.md](./main-ideas.md).

Облако (prod): [aws-data-architecture.md](./aws-data-architecture.md) — **RDS**, **DynamoDB**, **Redis**, **SQS**.

---

## 1. Scope MVP

| В scope | Вне scope (позже) |
|--------|-------------------|
| Календарь по дням, сумма ккал за день | Иконки блюд (генерация) |
| Список позиций за выбранный день | Widgets, Shortcuts, Action Button, Watch |
| Голосовой ввод (локальная модель на устройстве) | Облачная замена модели (заложить возможность смены) |
| Регистрация / вход, данные привязаны к аккаунту | HealthKit, экспорт, вода, цели (можно добавить отдельными итерациями) |

## 2. Стек

| Слой | Технология |
|------|------------|
| Мобильное приложение | **React Native (Expo)**, iOS-first |
| API | **Go** (HTTP REST для MVP) |
| Основное хранилище | **PostgreSQL** |
| Кэш / сессии | **Redis** |
| Локально на устройстве | Secure Store (токены), **SQLite** (кэш календаря + очередь офлайн-изменений) |
| Голос | **Локальная модель на iPhone** (распознавание/разбор речи на клиенте); на сервер уходит уже **структурированный результат** (текст + распознанные позиции), не сырой аудиопоток |

## 3. Где что хранится

### 3.1 PostgreSQL — источник правды (backend)

Все персистентные данные пользователя и дневника:

- **users** — id, created_at, настройки (часовой пояс, локаль).
- **auth_identities** — привязки входа (минимум **Sign in with Apple** для iOS; при необходимости email/пароль позже).
- **food_entries** — одна строка = одна позиция в дневнике: `user_id`, **календарная дата** (в TZ пользователя), название/описание, калории (и при необходимости БЖУ), `source` (`voice`), необязательный `raw_transcript`, `created_at`, `updated_at`, `deleted_at` (soft delete).
- **refresh_tokens** (или только id + hash в Postgres) — долгоживущие сессии; отзыв при logout.

Агрегат «ккал за день» для календаря: на MVP можно **считать в запросе** (`SUM` по `food_entries` за день); при росте нагрузки — материализованный день или кэш в Redis (см. ниже).

### 3.2 Redis — не основная БД

- **Access-token blocklist / session version** (опционально) или кэш валидации refresh.
- **Кэш read-модели календаря**: ключ вида `user:{id}:month:{YYYY-MM}` → JSON с суммами по дням; инвалидация при create/update/delete записи за затронутые даты.
- **Rate limiting** на API (особенно эндпоинты логина и bulk-sync).
- **Idempotency-Key** для повторов запросов с клиента (нестабильная сеть).

Долговременные данные дневника **не** держим только в Redis.

### 3.3 Устройство (Expo)

- **Expo Secure Store** — access/refresh JWT (или только refresh + короткий access в памяти).
- **SQLite** — последние загруженные дни/месяцы для UI календаря без сети; **outbox** (очередь операций: добавить/изменить/удалить позицию) с синхронизацией на Go API при появлении сети.
- **Локальная модель голоса** — weights/runtime на устройстве; конфиг «какая модель» — в приложении, без хранения аудио на сервере по умолчанию.

### 3.4 Что не храним на сервере (MVP)

- Аудиозаписи диктовки (если не понадобится для отладки — явный opt-in позже).
- Сырые веса модели — только на клиенте.

## 4. Поток данных (голос → календарь)

1. Пользователь диктует **в приложении** → локальная модель даёт текст и/или черновик позиций (название, порция, ккал — по возможностям модели на v1).
2. UI показывает подтверждение (минимальное; детали UX — отдельно).
3. Клиент отправляет в API **POST /entries** (или batch sync) с датой дня и полями позиции.
4. Go пишет в Postgres, инвалидирует Redis-кэш месяца, возвращает актуальную запись и при необходимости **день. total_kcal**.
5. Клиент обновляет SQLite и экран календаря/дня.

Смена модели (облако или другая on-device): меняется только **слой на клиенте** (adapter); контракт API для `food_entries` остаётся тем же.

---

## 5. Авторизация

- **Sign in with Apple** — основной способ для iPhone MVP.
- **JWT**: короткий access + refresh; refresh хранится в Secure Store, rotation на бэкенде.
- Все эндпоинты дневника — только `Authorization: Bearer`, `user_id` из токена, без передачи user id с клиента.

## 6. API (черновой контур)

| Метод | Назначение |
|-------|------------|
| `POST /auth/apple` | Обмен Apple token → access + refresh |
| `POST /auth/refresh` | Обновление access |
| `POST /auth/logout` | Отзыв refresh |
| `GET /calendar?from=&to=` | Суммы ккал по дням в диапазоне (для сетки календаря) |
| `GET /days/{date}/entries` | Позиции за день |
| `POST /days/{date}/entries` | Добавить позицию |
| `PATCH /entries/{id}` | Правка |
| `DELETE /entries/{id}` | Удаление (soft) |
| `POST /sync` (опционально) | Применить outbox с клиента одним запросом |

Формат даты: **ISO date** в календарной TZ пользователя (`profile.timezone`).

## 7. Решение по БД (итог)

| Вопрос | Решение |
|--------|---------|
| Где «все данные» дневника? | **PostgreSQL** |
| Зачем Redis? | Кэш календаря, rate limit, idempotency, вспомогательные сессионные ключи |
| NoSQL для pipeline / черновиков (prod AWS)? | **DynamoDB** — см. [aws-data-architecture.md](./aws-data-architecture.md) |
| Офлайн | **SQLite + outbox** на клиенте, синк в Postgres через Go |

## 8. Деплой (ориентир)

- Go API + Postgres + Redis — один окруженийный контур (Docker Compose для dev; prod — **RDS**, **ElastiCache Redis**, **DynamoDB**, **SQS** — детали в [aws-data-architecture.md](./aws-data-architecture.md)).
- Expo: EAS Build для iOS; secrets (API URL) через EAS env.
