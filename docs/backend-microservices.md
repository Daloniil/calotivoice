# CaloriVoice — бэкенд: микросервисы (гипотеза)

Документ фиксирует **экспериментальный** контур обработки голосового ввода через несколько микросервисов на **Go**. Это проверка гипотезы «цепочка STT → guard → извлечение сущностей работает достаточно хорошо», а не финальный продакшн-контур.

Связанные документы:

- [main-ideas.md](./main-ideas.md) — продукт
- [technical-spec.md](./technical-spec.md) — MVP (там голос **на устройстве**; этот документ описывает **альтернативный/дополнительный** серверный путь для R&D)

---

## 1. Цель

Пользователь диктует, что съел и что выпил. Система должна:

1. Превратить речь в текст.
2. Отсечь запросы вне тематики приложения и попытки злоупотребления (prompt injection, вывод чужих данных, jailbreak и т.п.).
3. Из текста извлечь структуру: еда, напитки, количества, краткие описания — без полноценного продакшн-пайплайна калорий (на первом этапе достаточно JSON для проверки идеи).

Язык реализации сервисов: **Go**.

## 2. Логическая цепочка

```text
[Мобильное приложение]
        │  аудио (или уже текст — см. §6)
        ▼
┌───────────────────┐
│  MS-3: STT        │  Speech-to-Text (распознавание речи)
└─────────┬─────────┘
          │  transcript (строка)
          ▼
┌───────────────────┐
│  MS-1: Guard      │  Безопасность и scope запроса
└─────────┬─────────┘
          │  allow → дальше; deny → ответ клиенту без LLM
          ▼
┌───────────────────┐
│  MS-2: Intake     │  LLM: разбор дневника питания из текста
└─────────┬─────────┘
          │  JSON (массив/объект позиций)
          ▼
[API / сохранение в Postgres — позже, вне scope первого прототипа]
```

**Порядок в пайплайне:** STT → Guard → Intake.

## 3. Микросервис 1 — Guard (безопасность и тематика)

### 3.1 Задача

Проверить **текст пользователя** (после STT) **до** вызова тяжёлой LLM:

- Запрос относится к **дневнику питания текущего пользователя** (что съел/выпил, уточнения порций, вопросы про свои записи в рамках CaloriVoice)?
- Или это **вне scope** / **злоупотребление**: чужие данные, системные инструкции, injection, jailbreak, exfiltration, явно нелегальные/вредоносные сценарии?

На раннем этапе достаточно грубой бинарной логики для прототипа:

| Решение | Смысл | Действие |
|--------|--------|----------|
| **allow** | В scope, не похоже на атаку | Пропустить в MS-2 |
| **deny** | Вне scope или атака | Не вызывать MS-2; вернуть клиенту безопасный отказ |

Позже решение можно обогатить: `reason`, `category`, `confidence`, отдельные флаги «injection» vs «off_topic».

### 3.2 Референс: Jeff (как «Jeff guard»)

Имеется в виду **[Jeff](https://jeffhub.ai/)** — небольшая **decision-модель** (~0.8B): один forward pass, **калиброванные вероятности** по заранее заданным вариантам ответа, без генерации свободного текста.

Для задач, близких к описанным:

| Компонент | Назначение |
|-----------|------------|
| **Jeff base v1.3** (`mstrasser/jeff-base`, revision v1.3) | Общая база |
| **Adapter `guard`** (`mstrasser/jeff-adapter-guard`) | Prompt injection, jailbreak, indirect injection, exfiltration — см. [guard adapter](https://jeffhub.ai/adapters/guard) |

Guard-адаптер закрывает **атаки на модель**, но **не** полностью заменяет проверку «только калории и мой дневник». Для scope CaloriVoice план:

1. **Слой A:** Jeff `guard` — отсекать injection / jailbreak / exfiltration.
2. **Слой B (кастомное решение на Jeff или второй классификатор):** choice-вопрос с критериями в духе Jeff API (`systemone`): варианты вроде `food_diary_ok` vs `off_topic_or_policy_violation`, с `state` = описание приложения («голосовой дневник калорий, только данные текущего пользователя») + `message` = transcript.

Jeff можно поднять локально (`jeff-serve`, либо **llama.cpp** + GGUF base + LoRA guard — см. [Running Jeff with llama.cpp](https://jeffhub.ai/docs/llama-cpp)). Go-сервис MS-1 тогда — тонкий HTTP-клиент + пороги по probability + агрегация слоёв A и B.

### 3.3 Альтернативы (если Jeff не подойдёт)

- **Meta Llama Guard** (через Ollama/vLLM) — шире по модерации, тяжелее и медленнее Jeff.
- **Собственный fine-tune** малой модели под бинарный «calorie app scope» — позже, если zero-shot + Jeff criteria недостаточны.

## 4. Микросервис 2 — Intake (извлечение из текста)

### 4.1 Задача

На вход: **разрешённый** transcript (русский/английский — уточнить при реализации).

На выход (черновой контракт для гипотезы):

```json
{
  "items": [
    {
      "kind": "food",
      "name": "молоко",
      "amount": { "value": 300, "unit": "g" },
      "notes": "optional free text"
    },
    {
      "kind": "drink",
      "name": "вода",
      "amount": { "value": 200, "unit": "ml" }
    }
  ],
  "raw_transcript": "…",
  "model": "…",
  "warnings": []
}
```

Требования v0:

- Не обязательно считать калории в БД — достаточно **структурированного списка** для ручной/автоматической проверки качества.
- LLM может быть **локальной** (Ollama, llama.cpp server, vLLM) с промптом + JSON schema / tool calling.
- MS-2 **никогда** не вызывается, если MS-1 вернул `deny`.

### 4.2 Go-роль

HTTP API, валидация JSON, таймауты, логирование без PII в открытом виде (на dev — по необходимости), вызов runtime LLM по HTTP/gRPC.

## 5. Микросервис 3 — STT (распознавание речи)

### 5.1 Задача

Аудио (формат уточнить: wav/mp4/m4a, sample rate) → **transcript**.

Типичное название задачи: **ASR / STT** (Automatic Speech Recognition / Speech-to-Text).

### 5.2 Локальные модели (ориентир для прототипа)

| Модель / стек | Плюсы | Замечания |
|---------------|--------|-----------|
| **Whisper** (OpenAI) через **whisper.cpp** или **faster-whisper** | Хорошее качество RU/EN, много примеров деплоя | Отдельный процесс или CGO; GPU опционален |
| **distil-whisper** | Быстрее, чуть хуже на edge cases | Для низкой латентности |
| **Vosk** | Лёгкий офлайн | Проще, но качество на диктовке «еда» нужно померить |

Go-сервис: приём multipart/audio bytes, очередь при необходимости, вызов STT worker ( subprocess / sidecar ).

### 5.3 Связь с MVP

В [technical-spec.md](./technical-spec.md) для MVP заложен **STT на iPhone**. MS-3 нужен, если проверяем **серверный** путь или гибрид (короткие клипы на сервер, модель тяжелее). Оба варианта могут сосуществовать: клиент шлёт либо audio → MS-3, либо text → сразу MS-1.

## 6. Репозиторий: каталог `backend/`

Планируемая структура (реализация — по мере спринтов):

```text
backend/
  README.md
  services/
    stt/      # MS-3
    guard/    # MS-1
    intake/   # MS-2
  deploy/     # позже: docker-compose, env-шаблоны
```

Общие для всех сервисов на Go (когда начнём код):

- Единый стиль: `cmd/<service>/main.go`, `internal/`, конфиг через env.
- Межсервисные вызовы на первом этапе — синхронный HTTP внутри docker-compose; оркестратор (API gateway) — опционально позже.

## 7. Нефункциональные требования (черновик)

| Тема | Направление |
|------|-------------|
| Секреты | API keys к LLM только в env; не коммитить |
| Латентность | Guard (Jeff) — целевой порядок **десятки ms**; STT и Intake — доминируют по времени |
| Данные | Аудио на v0 можно не персистить; transcript — минимально для отладки, с TTL |
| Наблюдаемость | request_id сквозной через STT → Guard → Intake |
